# 升级与恢复

升级前结束或明确暂停**所有**聊天与终端任务，保存需要的工作。重启服务会结束后台任务，历史记录不会使进程继续执行。按实际启动方式选择，不要混用。

## npm 后台启动器（npx / 全局命令）

「设置 → 通用设置 → 应用更新」可检查 npm 新版。由 npm 包的后台启动器运行时，「升级并重启」会将校验后的发行版本安装到 Pi 数据目录的 `pi-web/releases/`，重启后台并重新加载原地址。

- npx 和全局命令均支持；后续启动自动选用托管版本。
- **不会修改 npm 全局安装**，因此全局包版本与当前运行版本可能不同，核对设置页中的运行信息。
- 新版启动失败时启动器尝试恢复旧服务；不要因此假设所有工作都无损恢复。
- 新版 npm 包精确锁定已验证的 Pi SDK 对（当前为 1.3.0），启动器使用包内 CLI，不使用全局 Pi。桌面更新也保留其已验证的 SDK 对。

**0.1.30 → 0.1.31-alpha.5 的已知失败：** alpha.5 的宽泛 peer 依赖可能安装到 SDK 1.4.0，而 hosted adapter 只验证了 1.3.0，日志显示 `Hosted agent adapter requires verified SDK 1.3.0, got 1.4.0`。这不是单纯加载较慢；重试同一版本或延长等待时间无效。请等待包含精确 SDK 依赖的后续修复版本，再检查更新并升级；不需要删除会话、修改托管目录或降级全局 Pi。

### 更新偏好：稳定版 / 体验版

在「应用更新」中选择更新偏好，偏好保存到 Pi 数据目录，重启、刷新或换浏览器后仍然有效：

- **稳定版（默认）**：选择 npm `latest` 对应的正式版本。
- **体验版**：选择 npm `latest` 和 `alpha` 中版本较新的一个；正式版发布后也会正常跟进，不会停在旧 alpha。
- 选择偏好本身**不会安装或重启**。检查目标版本后，点击「升级并重启」。
- 如果当前 alpha 高于最新稳定版，选择稳定版后显示「切换到稳定版并重启」。点击后必须确认较低的目标版本，并先备份重要数据；数据格式不兼容时会拒绝切换，不会自动恢复或转换数据。
- 检查后如果发布目标或偏好发生变化，安装会停止，需重新检查；不会悄悄安装另一个版本。

**旧入口兼容性**：首次使用更新通道前，结束任务并将原始 npx/全局启动入口更新到支持本功能的稳定版（仅升级托管业务包不等于更新全局入口）。旧桌面外壳也须安装新版；缺少通道能力的外壳不会开放 alpha 更新。此偏好控制 npm **业务包**，不改变桌面菜单通过 GitHub Releases 更新外壳的渠道。

### 桌面 build 10 的通道限制

`0.1.28 / build 10` 支持稳定业务包更新，但不支持在下次启动时保留 alpha 选择。仅把业务包更新到 `0.1.38` 或更高不会改变这个外壳能力。需要先安装包含更新通道支持的新外壳，再选择「体验版」并在线升级；[build 11 已发布](https://github.com/chengzhiyi/pi-webapp/releases/tag/desktop-v0.1.39-b11)，支持保存体验版通道和所选版本。设置页在外壳不兼容时显示外壳版本及桌面下载入口。

首次从 build 10 升级时，先结束聊天任务并关闭终端，在旧应用退出时选择“停止服务并退出”，再替换应用并启动 build 11。只连接仍在运行的旧后台不会更新其通道能力标记；若已保留旧后台，请从原入口停止后再由新版桌面启动。

体验版会选择 `latest` 与 `alpha` 中较新的版本。例如 `latest=0.1.39`、`alpha=0.1.39-alpha.1` 时，目标仍是 `0.1.39`，因为正式版高于同一版本的预发布版；等更新的 alpha 发布后才会提供 alpha 升级。

### 保存确认超时

`Missing view flush acknowledgement; old version retained` 表示某个插件视图未在 15 秒内确认冻结并保存，版本切换已中止。先保存并关闭绘图或编辑器；刷新后遗留的失联视图，请在对应会话的「插件视图恢复」中核对本地副本，再选择「保留恢复记录并解除阻塞」，然后重试。不要删除图稿或数据目录。新错误信息会列出尚未响应的插件、会话和视图标识，不包含认证 capability。

### 源码版本与发布版本

仓库 `package.json` 是源码的发行基线，不是 npm 上最新已发布版本的实时镜像。CI 的 `scripts/prepare-release.mjs` 根据 npm dist-tags 分配版本，在临时检出目录修改 `package.json` 和锁文件，验证后发布原始 tarball；`.github/workflows/ci.yml` 有意不将版本提交推回分支。因此之前源码长期显示 `0.1.29`，但 npm 和设置页中的实际运行版本继续增长。本次将源码基线同步为 `0.1.39`，后续 CI 仍按已发布版本递增；桌面外壳另外使用 `desktop/release.json` 的构建号。

若页面未恢复：

```bash
npx pi-webapp status
```

全局安装可用 `pi-webapp status`。检查 `~/.pi/agent/pi-web/launcher.log`（Windows 为 `%USERPROFILE%\.pi\agent\pi-web\launcher.log`；自定义数据根目录见[配置](./reference)）。确认没有活跃任务后再按原入口启动；收集版本和脱敏错误反馈，**不要删除 `~/.pi` 或手改托管发行目录来“修复”**。

## 已有 Pi 中的 /web

此方式可看版本，但不能网页重启。结束工作后按 Pi 的包更新流程更新已安装扩展，例如在 Pi 终端外运行：

```bash
pi update npm:pi-webapp
```

使用安装时保存的来源；用 `pi list` 检查，`pi update --help` 核对已装版本的语义。当前 Pi 中无参数 `pi update` 更新的是 Pi 自身，不能当成扩展更新。回到 Pi 重载扩展或重启 Pi，再输入 `/web`。Pi 自身版本过旧时另行更新 Pi；不要把它和 pi-webapp 扩展版本混淆。

## 源码运行

更新可信源码后，在仓库根目录执行 `npm ci` 和 `npm run build`。启动器方式用 `npm run stop` 再 `npm run start`；`pi -e .` 方式重建后在 Pi 中 `/reload` 再 `/web`。仅刷新旧网页不会替换后端桥接。

## 桌面测试包

桌面应用与 Web 运行时版本分别核对。无发布者签名的测试包仅支持校验下载、Finder 手动安装，不会自动安装。退出旧应用，按需停止旧应用自有后台，再替换应用；外部兼容 Web 后台无需停止。见[桌面测试指南](./desktop)。
